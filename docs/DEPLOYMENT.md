# Deployment guide

ClueCrew needs a **Node web service** (Express + Socket.IO + SQLite) and — optionally — a
separate static frontend. This guide documents the free architecture that was actually
evaluated in **2026**, the trade-offs, and the exact steps.

## Chosen architecture

```
                     ┌──────────────────────────────┐
   Browser  ───────► │  Render Free Web Service     │
   HTTPS + WSS       │  • Express REST API          │
                     │  • Socket.IO (WebSockets)    │
                     │  • serves the built client   │
                     │  • SQLite file (ephemeral*)  │
                     └──────────────────────────────┘

   Optional split (same browser experience, extra caveats):
   Browser ──► Netlify static frontend (client/dist, VITE_API_URL=backend)
                  └──► Render backend (CORS + SameSite=None cookies)
```

**Recommended: one Render service that serves both the API and the built client.**
Single origin means no CORS problems, no third-party-cookie restrictions, and WebSockets
work over WSS out of the box. The Netlify split is supported (see Option B) but is only
worth it if you specifically want a CDN-hosted frontend.

### Free-tier facts that shaped this choice (verified September 2026)

| Fact | Impact |
| --- | --- |
| Render free web service: 750 instance hours/month, 0.1 CPU / 512 MB | Enough for party games (small rooms, in-memory state) |
| Spins down after **15 minutes** without HTTP **or WebSocket** traffic (since Feb 2026 WS messages keep it awake) | A game in progress keeps it alive; the next visitor after idle waits ~1 minute cold start |
| **Ephemeral filesystem** — SQLite is lost on restart/redeploy/spindown | Rooms are ephemeral by design; guest sessions and linked TikTok accounts reset on restart (see below) |
| Render free Postgres expires after 30 days | Not used |
| Persistent disks are a paid feature ($0.25/GB + $7/mo instance) | Not required; documented as an upgrade path |
| Netlify static hosting is free and always-on | Fine for the optional split frontend |

Why not other options: Fly.io/Railway/Koyeb no longer offer a durable always-free web
service with persistent storage; Vercel/Cloudflare Workers-style platforms cannot run a
stateful Socket.IO server. A single Render service is the only fully free setup that runs
this exact architecture.

**Durability options (pick one, all optional):**
1. Do nothing — everything resets when the service restarts (fine for casual play; the game
   itself is designed to recover rooms and players automatically).
2. Attach a Render persistent disk (paid instance) — SQLite becomes durable with zero code
   changes (`DATABASE_PATH=/var/data/cluecrew.sqlite`).
3. Move to a managed Postgres — requires porting `server/src/database/repositories.ts`
   (currently synchronous SQLite; documented as future work, not shipped untested).

## Option A — Render, single service (recommended)

1. Push the repository to GitHub.
2. In Render: **New → Blueprint**, select the repo. `render.yaml` is detected, and Render
   creates the `cluecrew` web service with `npm ci && npm run build`, `npm start`, and the
   `/health` health check.
3. Apply the Blueprint — **no manual values are required**. The server derives its public URL
   from Render's automatically injected `RENDER_EXTERNAL_URL`, so redirect URIs, CORS and
   first-party cookies (SameSite=Lax) configure themselves. `TOKEN_ENCRYPTION_KEY` is
   generated by the blueprint.
4. Wait for the first build (~2–3 minutes) and open the service URL Render shows
   (e.g. `https://cluecrew.onrender.com`). Check `https://<service>/health` →
   `{"status":"ok","service":"cluecrew",...}`.
5. Open the URL, create a game, join from a second device.

Optional: set `BACKEND_URL` / `FRONTEND_URL` / `ALLOWED_ORIGINS` explicitly (they always win
over the auto-detected URL) when you attach a **custom domain** or run a split deployment.

Manual alternative (no blueprint): New → Web Service → build `npm ci && npm run build`,
start `npm start`, health check `/health`, then set the same variables. Without a
`TOKEN_ENCRYPTION_KEY` the server refuses to start in production (by design).

## Option B — Netlify frontend + Render backend (optional)

1. Deploy the backend exactly as in Option A, but set:
   - `BACKEND_URL` = `https://<backend>.onrender.com`
   - `FRONTEND_URL` = `https://<your-site>.netlify.app`
   - `ALLOWED_ORIGINS` = `https://<your-site>.netlify.app`
   The server detects that the origins differ and switches session cookies to
   `SameSite=None; Secure` automatically, and CORS is enabled for the allowed origins.
2. In Netlify: **Add new site → Import from GitHub**. `netlify.toml` builds the client
   (`npm ci && npm --workspace @cluecrew/client run build`, publish `client/dist`).
3. Set the Netlify environment variable `VITE_API_URL=https://<backend>.onrender.com`,
   then trigger a redeploy (Vite inlines it at build time).
4. Verify: open the Netlify URL, create a room on one device, join on another.

**Caveat (why Option A is recommended):** with two different sites the session cookie is a
third-party cookie when the browser talks to the backend from the Netlify origin. Chrome
and Safari increasingly restrict those. ClueCrew still works because room membership uses
per-player reconnect tokens (not cookies), but TikTok account linking and CSRF-protected
writes can fail in browsers that block third-party cookies entirely. Single-origin avoids
the entire class of problems.

## Environment variables

| Variable | Aliases accepted | Default | Purpose |
| --- | --- | --- | --- |
| `NODE_ENV` | — | `development` | `production` enables secure cookies, CSP, `trust proxy` |
| `PORT` | — | `3001` | HTTP port (Render sets this automatically) |
| `BACKEND_URL` | `PUBLIC_URL` | `RENDER_EXTERNAL_URL`, else `http://localhost:<PORT>` | Public backend origin (OAuth redirect base) |
| `FRONTEND_URL` | `CLIENT_URL` | `RENDER_EXTERNAL_URL`, else `http://localhost:5173` | Where OAuth returns to the SPA |
| `ALLOWED_ORIGINS` | — | `FRONTEND_URL,BACKEND_URL` | CORS/CSRF origin allow-list |
| `TOKEN_ENCRYPTION_KEY` | `SESSION_SECRET` | dev key | 64 hex chars; **required** in production |
| `DATABASE_PATH` | `DATABASE_URL` (`file:` prefix supported) | `./data/cluecrew.sqlite` | SQLite file; PostgreSQL URLs are rejected with a clear message |
| `TIKTOK_CLIENT_KEY` / `TIKTOK_CLIENT_SECRET` | — | empty | Enable TikTok Login Kit + Display API |
| `TIKTOK_REDIRECT_URI` | — | `{BACKEND_URL}/api/auth/tiktok/callback` | Must match the TikTok app registration exactly |
| `TIKTOK_DATAPORTABILITY_ENABLED` | — | `false` | Only enable after TikTok approves Data Portability |
| `TIKTOK_DATAPORTABILITY_SCOPE` | — | `portability.all.ongoing` | Minimum scope that includes likes/saves |
| `DP_*` | — | see `.env.example` | Import tuning (poll interval, caps, oEmbed) |
| `APP_VERSION` | — | `1.1.0` | Reported by `GET /health` |
| `VITE_API_URL` (client only) | — | empty | Absolute backend origin for split deployments |

Never commit real values. On Render set secrets in the dashboard; `render.yaml` uses
`generateValue` for the encryption key and `sync: false` for everything else.

## TikTok production setup

1. TikTok developer app → products: **Login Kit**, **Display API**, and (only if you want
   real likes/saves) **Data Portability API**.
2. Scopes: `user.info.basic`, `video.list`, plus the portability scope after approval.
3. Redirect URI in the TikTok console must equal your configured `TIKTOK_REDIRECT_URI`
   (defaults to `https://<backend>/api/auth/tiktok/callback`). HTTPS, static, no query.
4. Restart/redeploy the service, open the lobby, click **Continue with TikTok**.
5. Data Portability has its own review (3–4 weeks, UX mockups, privacy review) and only
   returns data for TikTok users in the EEA/UK. Until it is approved, liked/saved modes
   stay on clearly-labelled demo data — see `docs/TIKTOK-DATA-PORTABILITY.md`.

## Verification checklist after deploying

1. `GET /health` returns `{"status":"ok","service":"cluecrew","version":"…"}`.
2. `GET /api/config` returns public configuration only (no secrets).
3. Create a room on device A → code `ABC123`.
4. Join the same code on device B → both players appear live.
5. Start a game, answer rounds, watch the reveal and leaderboard stay in sync.
6. Lock the phone / reload a tab mid-game → player reconnects with the same state.
7. Finish the game → **Play again** starts a new game without reconnecting.
8. `npm run smoke` against the deployed URL if you want an automated pass
   (`npm run simulate -- https://<service> 5 3` uses real WebSockets).

## Troubleshooting

| Symptom | Cause / fix |
| --- | --- |
| Service exits: `TOKEN_ENCRYPTION_KEY is required in production` | Set the secret (or let the blueprint generate it) |
| `403 CSRF_FAILED` | The site origin is missing from `ALLOWED_ORIGINS` |
| OAuth redirect error | `TIKTOK_REDIRECT_URI`/TikTok console mismatch, or a non-HTTPS URL |
| 1-minute first load after idle | Free tier cold start — expected behaviour |
| Rooms/accounts vanish after a restart | Free tier has an ephemeral filesystem; see durability options above |
| WebSockets not connecting through your own proxy | Ensure upgrade headers are forwarded (Caddy/Nginx defaults are fine) |
| `DATABASE_URL points to PostgreSQL…` | This build is SQLite-only by design; use a file path |
